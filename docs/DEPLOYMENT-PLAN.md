# VT v0.1 封闭试用部署 Plan

日期：2026-09-18。状态：**方案待确认，尚未部署**。

本轮只保存已联调版本、制定部署与验收方案。没有新增功能、调整 UI、推送代码、创建托管项目、购买服务、修改 Auth 或写入远端数据库。已成功应用的 `001_initial.sql`、`002_training_copy.sql` 不再执行。

## 推荐方案

采用 **Vercel 的 Next.js 托管 + 现有 VT-dev Supabase + 私有 GitHub 仓库**，先邀请 5–10 人，开展至少 7 个北京时间自然日的封闭试用。

选择理由是当前项目已有 Node.js API、Supabase 适配及成功的 production build，使用 Next.js 原生托管可减少部署改造。此次部署不创建新数据库，不迁移或清空现有数据。SQLite 只由本地模式动态加载；测试站必须使用云端模式，不能部署成纯静态网站。

先发布受保护的 Preview，固定一个测试网址，在整轮自然时间观察期间保持版本和网址稳定。使用 Vercel Authentication 保护部署，并由负责人私下发放可撤销的共享访问链接；测试者通过链接进入后，仍须登录自己的 VT 账号。共享链接持有人可转发链接，因此它不是逐人身份白名单，也不能替代 Supabase 账号权限。Hobby 每个账号只能创建一条共享链接。若以后采用固定主域名，须确认保护范围为 All Deployments，避免默认 Standard Protection 留下未保护的主域名。[部署保护](https://vercel.com/docs/deployment-protection)、[共享链接](https://vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/sharable-links)。

建议优先使用已有域名的测试子域名；没有域名时可先验证受保护的 Preview 地址。Vercel 官方明确不保证中国大陆的可用性；更换自有域名也不保证 Supabase Auth 可达。**大陆普通网络实测是扩大试用前的必要条件**。若不通过，暂停扩大范围，再单独评估其他托管地区或服务商，本轮不更换架构。[大陆访问说明](https://vercel.com/kb/guide/accessing-vercel-hosted-sites-from-mainland-china)。

## 构建与运行

| 设置       | 方案                                                                  |
| ---------- | --------------------------------------------------------------------- |
| Framework  | Next.js                                                               |
| Node.js    | 固定选择 24.x，不使用 Edge Runtime                                    |
| Install    | `npm ci`，使用已提交的 lockfile                                       |
| Build      | `npm run build`                                                       |
| 输出与启动 | 保留 Vercel 的 Next.js 默认输出和托管运行方式，不手工执行 `npm start` |
| API        | 必须部署 `/api/training` 的 Node.js 服务，禁止静态导出                |
| 数据库     | 连接现有 VT-dev；构建、发布流程不得添加 migration 命令                |

Vercel 支持 Node.js 24.x。[运行时说明](https://vercel.com/docs/functions/runtimes/node-js/node-js-versions)。当前仓库的 `npm start` 是本地启动方式，绑定 127.0.0.1；若以后改用普通 Node 主机，需要按其端口和监听地址要求另定启动命令，不直接套用本地命令。

按已保存的具体 Git 提交创建候选部署，记录提交、平台 Deployment ID、测试网址及迁移版本。先确认云端模式、未登录请求被拒绝、健康登录和保存，再发放给测试者。函数区域在确认 VT-dev 所在区域后选择，平台默认区域不视为已优化。Vercel 实际构建、代理后的 Origin/Host 校验与运行情况均需在测试网址验收，不能用本地 build 代替。

## 环境变量（只列名称）

| 名称                                   | 用途                                             |
| -------------------------------------- | ------------------------------------------------ |
| `NEXT_PUBLIC_DATA_MODE`                | 明确启用云端数据模式，不能缺失而落入访客本地模式 |
| `NEXT_PUBLIC_SUPABASE_URL`             | 指向既有 VT-dev                                  |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | 当前标准的 Supabase 公开客户端配置               |

旧 `NEXT_PUBLIC_SUPABASE_ANON_KEY` 仅是兼容 fallback，新部署不需要同时配置。无需配置 `VT_DB_PATH`、service role、secret key、数据库密码或管理访问令牌；SMTP 凭据如获批准，应配置在 Supabase 发信设置中，不添加到前端环境变量。

上述公共配置在构建时进入客户端产物，应先配置正确的 Preview 环境再构建；未来若发布到另一平台环境，须单独核对对应配置。变更后需重新构建，单纯重启不能更新已生成的客户端配置。公开 key 不能代替 RLS，不能将高权限 key 填进公开变量。

## Supabase Auth 与测试账号

本轮只读检查确认：Email 登录启用、注册开启、邮箱自动确认关闭，即普通注册仍要求验证邮箱；没有改动这些设置。现有真实联调证明的是**管理员预确认账号的 Email + Password 登录**，不是邮件验证闭环。

审批后，按最终测试网址设置：

- Site URL：固定的测试站 HTTPS Origin。
- Redirect URLs：精确允许同一 Origin 下的 `/login`，保留仍在使用的已批准开发地址；不放开任意域名通配符。
- 当前注册代码使用 `origin + /login`。不存在 `/auth/callback`，不要配置或承诺不存在的回调处理流程。
- 如果切换 Preview 地址或测试域名，须重新确认 URL 配置，并在新地址实测；含访问令牌的共享链接不要填入 Site URL 或提交到 Git。

这些都是**待确认的 Auth 配置变更**。[Supabase Redirect URLs](https://supabase.com/docs/guides/auth/redirect-urls)。

首轮推荐管理员为每名受邀测试者预建独立、已确认的试用账号，由负责人通过私密渠道分别提供登录标识和随机密码。测试者访问受保护的测试网址，再通过现有登录页登录；不要共享一个账号，也不要复用包含历史夹具的 A/B 联调账号。产品目前没有邀请设密、忘记密码或重设密码页面，首轮不把这些流程列为已有能力。

为将注册范围限定在受邀账号，建议批准后关闭 Supabase 的 Allow new users to sign up，保留 Email + Password 登录；完成账号准备后先验证受邀账号仍可登录、普通注册被拒绝。现有 UI 注册入口不改，封闭试用说明中告知使用发放的账号。[注册配置说明](https://supabase.com/docs/guides/auth/general-configuration)。本轮尚未关闭注册或创建新试用账号。

**邮箱验证当前为未验证，不能宣称可用。** 本轮未检查或修改项目 SMTP 私密设置。若使用 Supabase 默认发信，它仅向项目团队预授权地址发信，目前限制 2 封/小时，不能作为外部测试者的可靠注册通道。不要为了收邮件把测试者加入 Supabase 管理团队。[SMTP 限制](https://supabase.com/docs/guides/auth/auth-smtp)。

若你希望本轮试用同时验收注册邮件，需先批准自定义 SMTP、发信域名设置及限定时间的注册配置调整，再用真实测试邮箱完成“收到邮件 → 点击确认 → 返回测试站 `/login` → 登录”。页面提示已发信不算通过。管理员预确认不计作邮箱验证通过。

| 编号 | 实际测试步骤                                                                 | 通过条件                                                                                                            |

## 失败与恢复

1. 发布前记录候选 commit、部署 ID、当前可信部署、目标环境和迁移版本。构建失败时不发放该版本，原可用网址继续使用。
2. Preview 试用失败时恢复到先前验收过的 Preview 及其受保护访问入口；Hobby 只有一条共享链接时，由负责人重新分配并撤销失败版本的入口。域名或回调有变化，先批准对应调整再切换。
3. 若后续采用固定主域名，使用平台 Instant Rollback 指向上一可用构建；Hobby 只能回到紧邻上一版，Pro 可选符合条件的旧部署。没有上一份线上版本的首次部署失败，只能停止发放网址、保持未上线，不能声称已经完成线上回滚。[回滚说明](https://vercel.com/docs/instant-rollback)。
4. 应用回滚不会回滚 Supabase 数据、Auth 配置或秘密值；旧构建仍含其当时的公开配置。回滚后重新验证目标项目、登录、读取与保存。若环境配置有误，修正后重新构建，不仅重启。
5. 全程保留现有 `001 + 002`，不重跑、不逆向删除业务数据。涉及数据库恢复、清理数据或 Auth 再调整时，另行提出具体操作并等待确认。
