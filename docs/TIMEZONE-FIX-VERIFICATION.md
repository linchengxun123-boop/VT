# 北京时间训练日期修复与安全复核

日期：2026-09-18。

**结论：客户端可控时区问题已修复，本地复核未发现仍需阻塞执行的已知问题。建议在用户明确批准后，向此前确认的空 VT-dev 业务库依次执行更新后的 001 与原有 002。当前尚未执行任何远端 migration。**

本报告替代修复前安全复核中“时区问题仍然阻塞”的结论；修复前报告作为审计历史保留。

## 修复内容

- `src/lib/streak.ts`：使用无时区参数的 `trainingDate(now)`，固定 Asia/Shanghai。传入的 now 仅来自服务端时钟；客户端无法调用 API 指定它。
- `src/lib/server/repository.ts`：不再读取 x-timezone；不读取客户端日期、查询参数或时区决定 today。本地读取与写入使用北京时间；云端读取在生成 snapshot 时计算北京时间，避免沿用认证或写入前的旧日期。
- `src/components/training-provider.tsx`：移除客户端时区 Header。
- `001_initial.sql`：`vt_action` 从三参数改为两参数 `(p_action text, p_payload jsonb)`，同步更新 REVOKE / GRANT 函数签名。新建数据库中只存在两参数版本。
- 数据库内部固定执行 `(now() AT TIME ZONE 'Asia/Shanghai')::date`，存入同一个 v_today；daily_progress、checkins、当日完成校验与打卡锁定全部复用该值。
- 直接 RPC 传入第三个参数或命名 p_timezone 无法匹配函数；payload 中伪造 date、checkin_date、timezone、p_timezone 不会参与日期计算。
- streak、本周训练天数和今日是否打卡继续使用服务器返回的 today 与记录 date，统计算法本身未改变。

没有改变五张表的结构、任务 ID、训练计划、训练时长、推荐规则、用户记录或既有 RLS 策略。002 未修改。

## 重新执行的安全复核

- 五张业务表 RLS 全部启用，仍为两条公共训练内容读取策略与三条本人数据读取策略。
- 普通角色无直接写表权限，30 次 INSERT / UPDATE / DELETE 均拒绝；有效权限检查未授予 TRUNCATE 等额外权限。
- SECURITY DEFINER 固定空 search_path，拒绝空 auth.uid()，普通调用者不能冒充其他用户；匿名角色无法执行 RPC。
- 未全部完成任务时，函数拒绝打卡；客户端伪造完成数无法绕过。
- 两个复合 UNIQUE 约束有效；打卡后任务锁定、重复 RPC 幂等。
- 001 失败整体回滚；002 失败回滚文案更新。两份脚本各自独立事务。
- Seed 仍为三计划、十任务；001 重跑报错，不会产生重复记录；002 重跑结果不变。
- 新 001 不保留可传时区的函数重载，直接修改会话时区或请求输入不能改变中国自然日。

五条 SELECT policy 仍适用于“普通客户端只读、写入通过受控函数”的设计；没有新增写 policy 或扩大客户端权限。
